# PoC 库

本工作区自有的 PoC 库，按**披露状态**分两类。与 `knowledge/`（接地知识，
只存识别签名+弱点锚点）不同，这里存**可运行的验证工具**——但同样受
`src-safety-boundary` 与 `.claude/hooks/` 硬边界约束：证明存在即停，
不做不可逆危害。

## 分类

```
poc_library/
├── normal/   普通 PoC —— 配置依赖、条件性、已知技术应用。
│             漏洞根因是部署配置（可开可关）或依赖外部条件（如密钥），
│             更换目标可能需要重新适配。
│
└── xday/     通杀 PoC —— 产品代码/框架级缺陷，全版本/全实例通杀。
              漏洞根因在代码中（非配置可关闭），批量复现确认普遍性，
│             PoC 仅需替换 --target 即可工作。敏感，外发须混淆/脱敏。
```

### 判定：放 normal 还是 xday？

| 条件 | normal | xday |
|------|:--:|:--:|
| 已有公开 CVE/CNVD 编号 | ✅ | — |
| 公开 PoC/利用已存在 | ✅ | — |
| 漏洞根因是部署配置（可开可关） | ✅ | — |
| 漏洞依赖外部条件（密钥/账号/特定环境） | ✅ | — |
| 自主发现、尚未披露 | ✅ | ✅ |
| **通杀**：代码/框架级缺陷，全版本影响，多实例批量确认 | — | ✅ |
| PoC 仅需替换 target 即通用 | — | ✅ |
| 厂商已发布补丁 | ✅ | — |
| 提交流程中/待修复 | — | ✅ |

**通杀判定标准**：漏洞是产品代码写死的缺陷，还是配置/条件依赖的？
- 代码级（框架漏了鉴权拦截器、参数拼接SQL）→ xday，换了同产品其他实例仍有效
- 配置级（注册页面没关、密钥用了默认值）→ normal，换个部署可能就不同了

⚠️ **分类与机密性是独立维度**：normal 中未公开披露的条目（厂商未修复、无 CVE/CNVD）
同样不进仓库——在 `.gitignore` 中单独登记，与 xday 同等保密。已公开披露的 normal 条目
可以随仓库发布。

状态会变：xday 一旦公开披露并修复，移到 normal 并更新条目状态；同时从 `.gitignore`
移除、加入公开索引。

## 条目结构

每个漏洞一个目录：`<分类>/<漏洞id>/`
- `README.md` — 元数据表（产品/厂商/类型/危害/状态/影响版本）+ 原理 + 用法 + 安全约束
- `poc.py` / `poc.go` / 二进制 — 验证工具
- 关联 `knowledge/<id>.md`（接地知识）与 `runs/<...>/`（复现台账）

## 外发纪律

- **未披露条目（xday + normal 中未公开的）一律留本地、不进仓、不 push**
  （方法自由是指允许编写，不等于必须发布）。`.gitignore` 强制拦截。
- **已公开条目（CVE/CNVD 已分配、厂商已修复）** 可以随仓库发布。
- 外发披露平台（CNVD/EDUSRC 等第三方）时纪律更紧:用**混淆二进制**
  （`poc_*.exe` / `poc_linux64`，garble -literals，`strings` 零泄露），**不外发源码**。
- 漏洞描述脱敏：交平台的文字描述按需隐藏利用原理（见对应 run 目录的提交稿）。
