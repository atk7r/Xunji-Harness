# 寻迹 Xunji：AI 武器化红队工作区项目介绍

## 1. 项目定位

寻迹（Xunji）是一个由 Claude Code 作为唯一自主驱动的 Web 初始访问红队工作区。给定一个授权目标后，它能够自行推理、选择工具、执行验证、沉淀证据并起草报告，整个过程不依赖操作者持续喂给“下一步该做什么”。

它的核心战场是 Web 层，也就是 HTTP、浏览器、前端资源、接口、认证流程和业务逻辑。项目目标不是简单发现“疑似漏洞”，而是把漏洞证明到证据足够的位置：证据需要多深，验证就推进到多深；证不到，就不能算数。

一句话概括，寻迹不是一个 payload 扫描器，而是一个会推理的攻击者。它不内置固定清单，不依赖固化 playbook，也不把同一套 payload 不分目标地打一遍。项目真正排斥的，是盲扫、机械化剧本和脱离目标语境的批量尝试。它追求的是基于目标特征、运行证据和攻击前沿的自主判断。

## 2. 设计哲学：只给模型三样东西

寻迹并不试图把“怎么打”写死。相反，它只给模型三类东西，然后让模型像一个有纪律的人类渗透测试员一样推进任务。

第一类是判断纪律。它规定模型如何推理，如何区分“疑似”和“确认”，什么时候应该继续深挖，什么时候应该更换前沿，什么时候必须承认当前证据不足。这里关注的不是某个具体漏洞怎么测，而是攻击过程中的认知纪律。

第二类是接地知识。项目维护产品指纹、弱点锚点、漏洞类别、机制说明以及 CVE/CNVD 等参考信息。这样模型在识别出某个产品或技术栈后，可以调用对应的弱点知识进行定向分析，而不是只凭模型记忆猜测。

第三类是硬边界。模型可以展开攻击推理，可以编写验证逻辑，也可以围绕授权目标构造证明路径，但自动执行必须受到运行时机制约束。项目控制的不是“模型能不能想到某种方法”，而是“系统能不能自动对真实目标造成不可逆危害”。

因此，寻迹的框架角色不是压低模型能力，而是把模型能力约束成可信产出。发现阶段可以开放、创造、发散；确认阶段必须证据绑定、可归因、可复核。

## 3. 上下游分工：观澜负责侦察，寻迹负责攻击

寻迹不承担 OSINT 侦察本身。信息收集由上游独立工具观澜（Guanlan）完成。观澜负责采集资产、去重、折叠通配 DNS、探活、归属分类，并输出一份干净的资产清单。

寻迹消费这份清单，直接进入攻击验证阶段。`setup_run` 会把观澜产物零重探地折叠成 coverage 台账，派生 scope，建立运行目录，然后把工作流交给 AI 驱动器继续推进。

这条边界是项目近期理顺的重要主线。早期框架中，寻迹会用自己的工具重复做一部分观澜已经完成的侦察工作，造成空转。现在的设计把职责切开：观澜负责“看见资产”，寻迹负责“打穿证据”。

## 4. 一次 run 如何运行

每个授权目标都会维护一个 `runs/<目标>_<日期>/` 工作目录。这个目录不是临时输出，而是整个调查过程的审计轨迹。攻击过程不允许只停留在聊天上下文里，所有关键判断、证据、前沿和结论都要写入运行目录。

一次标准运行从 `setup_run` 开始：创建目录骨架，记录 recon 输入，派生 scope，生成 coverage 台账。随后进入持续工作循环：

```text
观察目标
-> 更新攻击面、前沿和假设
-> 在整张前沿上重新推理
-> 选择一个安全的验证动作
-> 记录证据
-> 进行假阳性检查
-> 继续、确认或否决
```

其中，“在整张前沿上重新推理”是每轮都会执行的低成本复盘。它要求模型反复检查：新证据是否解锁了某个被忽略的方向？是否推翻了某个原本看似可行的假设？当前是否过度钻进一个前沿，却把更高价值的资产或入口晾在一边？

驱动纪律可以概括为：高价值先深挖，随后自动铺开广度，再进入更深层验证。只要仍然存在安全的开放前沿，系统就不应该停下来询问操作者下一步测什么，而应当自行选择方向，并把选择理由写入 `decisions.md`。

## 5. 双重心智与证据门

寻迹在工作时具有两种内部心智。

第一种是红队心智：不要过早收手，把阻碍当成信息，持续扩大攻击面，寻找组合路径和替代入口。

第二种是猎人心智：不要过早相信，给每个信号归因，区分“证明”和“怀疑”，拒绝证据支撑不住的结论。

这两种心智共同服务于一个原则：发现可以发散，确认必须收敛。

项目中的确认闸门是 `certainty >= 0.8`。单次观测、环境自带痕迹、拦截页、重定向、异常状态码、模型自信，都不能单独作为确认依据。一个信号在进入证据链之前，必须回答几个问题：它是不是由本次动作造成的？是否存在对照？是否能复现？是否能排除页面原有状态、缓存、WAF、跳转和误读造成的影响？

因此，寻迹更偏好布尔差异、受控对照和可复现探测。证据不是“看起来像”，而是“这次动作导致了可解释、可归因、可复核的变化”。

## 6. 知识库与指纹飞轮

寻迹的知识分为两层。

第一层是公开接地层，位于 `knowledge/*.md`。这一层可以随仓库发布，内容包括产品识别签名、弱点锚点、验证要点、漏洞类别和机制说明，但不包含可直接复用的 payload。

第二层是本地武器化层，位于 `knowledge/weaponized/`，并被 git 忽略。这一层用于保存 payload、利用链和 PoC 等敏感材料。它可以在本地授权测试中使用，但不作为公开项目内容发布。

这套分层的关键不是否认武器化能力，而是把“可公开的接地知识”和“不可公开的直接利用材料”分开。公开层帮助模型识别目标、锚定弱点、建立准确术语；本地层服务于授权场景下的深度验证与利用研究。

项目还设计了知识飞轮：实战中识别出某个产品后，`knowledge_match` 会取出对应弱点锚点，辅助模型定制下一步验证；如果识别出清晰指纹但知识库中还没有记录，则通过 `knowledge_seed` 写回。这样，知识库会随着真实运行不断变厚，下一次遇到同类目标时，模型的识别和推理会更快、更稳。

## 7. 主动验证工具与护栏

寻迹的主动能力集中在 `tools/` 目录中，例如：

- `probe.py`：发送请求，验证差异，支撑证明型 payload。
- `render.py`：使用无头浏览器处理认证后页面、前端渲染、DOM 行为和 SPA 场景。
- `scan.py`：把 sqlmap、nuclei 等工具当作传感器，而不是最终结论来源。
- `fetch_assets.py`：枚举并抓取 SPA chunk，减少隐藏端点和前端路由遗漏。

这些工具不会绕过框架裸奔，而是统一经过 `tools/harness/guard.py`。guard 层提供限速、响应体上限、爆破锁、上传清理和会话预算等保护机制。任何新主动能力都应继承这层护栏。

这也是项目区分“AI 武器化”和“自动化失控”的关键：模型可以选择工具，可以构造验证，可以推进攻击前沿，但执行层必须留下记录，并受到可检查的工程约束。

## 8. 防自欺的收口机器

寻迹最特别的部分之一，是它不仅防外部风险，也防模型自己。

AI 智能体在长期任务中容易出现一种问题：在已经投入大量上下文后，它会倾向于过早宣布“测完了”，把证据不足包装成“没有发现”，或者把“暂时打不动”误写成“已排除”。这不是能力问题，而是自评偏差。

为了解决这个问题，项目引入了 `check_run.py` 和 Stop hook（`run_gate.py`）组成的收口门。收口时，系统会强制审查 run 文件：每个可达资产是否都有明确 verdict；只有指纹而没有攻击验证的资产，不能算真正测过；带攻击面的资产如果被 deferred，必须附带攻击证据，否则就是把“没打”伪装成“收口”。

同时，项目还引入独立复审机制。因为自评无法治愈自评偏见，关键收口需要由新上下文的 reviewer 重新审查运行痕迹。这套机制不是一开始凭空设计出来的，而是在真实 dogfood 中，被一次次复审抓到过早收口问题后逐步焊出来的。

## 9. 安全模型

寻迹的限制不写在主文档里，而是声明在 `src-safety-boundary` skill 中，并由 `.claude/hooks/` 的 PreToolUse 门强制执行。

这套安全模型守的是效果，而不是方法。模型可以为授权目标进行深度攻击研究和完整利用代码编写，这属于 author-and-handoff：框架负责把代码、思路和证据交给操作者，由操作者在监督下决定如何运行。系统自动对活目标执行时，则默认止于证明级。

真正被硬拦的是不可逆危害，例如销毁、删库、拖库、DoS、资金操作、删除资源和越权修改权限等。换句话说，项目不靠禁止术语来制造安全感，而是用运行时硬边界阻断不可接受的效果。

此外，`sentinel/` 子系统负责观察运行时行为、归因风险和记录异常趋势，但它本身不拦截。硬阻断、工具护栏和行为观察三者分工明确，共同构成寻迹的安全模型。

## 10. 项目价值

寻迹的价值不在于又封装了一套扫描器，而在于探索了一种 AI 武器化红队系统的工程形态。

它把 AI 放在攻击链的中枢，让模型负责推理、选择、验证和报告；把知识库作为接地层，让模型面对真实产品和真实技术栈时不靠空想；把 run 目录作为审计轨迹，让结论来自证据，而不是聊天记忆；把 guard、hook、sentinel 和 review 作为控制系统，让自主攻击能力不会滑向不可控执行。

因此，寻迹可以被理解为一个受控的 AI 攻击者原型：它承认并利用 AI 的武器化潜力，但又用工程机制把这种潜力压进可记录、可审计、可复核、可收口的工作流里。
