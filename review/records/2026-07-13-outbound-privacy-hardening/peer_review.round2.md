- [claude] **Enforcement ordering gap in safety_gate.main():** The cleanup check `cleanup_requires_ask` is evaluated BEFORE the privacy check ranking. If both trigger, only the "ask" prompt is shown, not the hard privacy "deny". A redesign that checks privacy FIRST (regardless of cleanup status) or adds a distinct privacy-flagged ask would close this gap without blocking legitimate cleanup.
- [claude] **The `_decoded_variants` token limit of 32** for base64 and hex detection could be exhausted in unusual payloads, but this is a low-practical-risk edge case since normal outbound requests don't carry that many candidate tokens.
- [claude] **No end-to-end multi-hop redirect test with a real HTTP server** — the redirect handler is unit-tested with synthetic `Request` objects. A live test with a server returning 302 chains would provide stronger validation that Cookie/Authorization is actually stripped on the wire, not just in Python objects.
- [claude] **render.py Playwright route error aggregation:** Only the first privacy violation error is raised (`privacy_blocks[0]`). If a page triggers 3 blocked sub-requests, only the first is reported; the other two are silently aborted. This could mask what exactly was blocked.
- [claude] **No `--allow-sensitive-auth` annotation on `tools/scan.py`** — if a scanner is pointed at an authenticated endpoint, there's no way to pass credentials through the privacy guard via scan.py. This is consistent with scan being a proof-level tool, but it's worth noting as a deliberate design constraint.

The `privacy.py` selftest does indeed test percent-encoded (`x%75nji-proof`), base64 (`eHVuamk=`), hex (`78756e6a69`), case (`XuNjI-proof`), and NFKC (`ｘｕｎｊｉ-proof`).
