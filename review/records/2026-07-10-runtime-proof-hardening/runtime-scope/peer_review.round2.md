## Blind-spot check
- [claude] **[BLIND-SPOT] The `review.md` was committed as a pre-written template that claims evidence not yet generated.** The pattern of writing "is stored as `peer_review.md`" before the independent reviewer has produced output is a process hazard — if the reviewer's output were lost, the run would appear to have passed independent review based on a false claim. The review.md should describe what is EXPECTED (future tense) or be written AFTER the review completes.
- [claude] **[BLIND-SPOT] `runtime_observation.py:16` computes `ROOT = Path(__file__).resolve().parents[3]`** — from its frozen location at `review/records/2026-07-10-runtime-proof-hardening/runtime-scope/runtime_observation.py`, this resolves to `review/` rather than the repository root. The script's import of `TOOLS = ROOT / "tools"` (line 17) would fail if executed from its archived path. The observation output was generated when the script lived at a different location. This means the frozen `.py` artifact is not independently reproducible from its recorded location — you would need to move it to the repo root or adjust the path. The observation JSON output is the true evidentiary artifact, not the script.
- [claude] **[BLIND-SPOT] The `probing`/`working` status expansion to active fronts is technically correct** (excluding them allows relabel evasion, as `context.md:12-14` explains), but it's a **silent operator-facing behavioral change**. An operator who marks a front `probing` to indicate "exploring, not actively pushing" would be surprised when it triggers Agent Board fanout requirements. The rationale is in `context.md` and `evidence.md:8` but nowhere in settings or hook messages is this semantic change surfaced to the operator at runtime. The statusline/anti_drift reminder reads the same regardless.
- [claude] **[BLIND-SPOT] The fail-closed shift removes a safety net but adds a sharp edge.** `disposition.md:36-38` explicitly rejects automatic fail-open recovery: "Automatic fail-open is intentionally rejected: it converts hook breakage into an unobserved process bypass." This is a defensible security posture, but it means: if a Python dependency update breaks `turn_contract.py` import, every subsequent Claude session with an active run will be blocked by output_gate and run_gate with no automatic path to recovery. The operator must manually deactivate the active run or fix the hook. The disposition acknowledges this as an explicit design choice ("Recovery is an explicit operator/local-maintenance action"), which is fair but worth flagging as an operational risk.
- [claude] **[BLIND-SPOT] The 57/57 selftest pass in `selftest_all.log` confirms no regressions**, but the `output_gate` selftest (0.4s) and `run_gate` selftest (1.2s) test logic in isolation — they don't verify the hooks actually fire correctly within a real Claude Code session. The `runtime_observation.py` partially fills this gap by calling `turn_contract.py` as a subprocess with Claude-shaped events, but it still runs in a temp directory. A live Claude Code session with the installed hooks remains the final integration test.
- [claude] **[BLIND-SPOT] The evidence ledger has no negative results.** Every entry is confirmed with certainty ≥ 0.8, and every `supports`/`refutes` array is empty. This is unusual in a security review — real hardening work typically has some "we tested X, it didn't work, here's why" entries. The absence of negative evidence doesn't invalidate the positive evidence, but it suggests the review focused exclusively on confirming expected behavior rather than actively searching for bypasses that the code changes DON'T catch. For example: does the hook wiring handle hook execution ordering? Does the PreToolUse contract fire before the safety_gate? What happens if a tool call name doesn't match the matcher regex? These negative-path tests don't appear in the evidence.
